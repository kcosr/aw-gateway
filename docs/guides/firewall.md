# Firewall Policy Guide

This guide describes generic ways to attach firewall policy to an `aw-gateway`
target. It intentionally avoids any site-specific proxy product or allow-list
syntax. Use it as the network-policy layer on top of the Podman, Docker, or
Colima deployment guides.

Firewall policy is optional. The base guides leave egress unrestricted so the
container runtime and SSH path can be validated before policy is added.

## Policy Placement

There are three common places to apply rules:

| Placement | Best For | Tradeoff |
|---|---|---|
| Host step targeting the container network namespace | Managed Linux Podman/Docker hosts | Strongest admin control; requires host privileges such as `sudo nsenter`. |
| Container bootstrap step | Local or self-managed containers | Easier to package; requires in-container tools and capabilities such as `CAP_NET_ADMIN`. |
| Runtime/VM-level rules | Colima or shared Docker bridge policy | Applies outside the container; can affect multiple containers on the same bridge/profile. |

Prefer host or VM policy for restrictions the user must not be able to remove.
In-container rules are convenient, but a container user with root and
`CAP_NET_ADMIN` can change them.

## Gateway Hook Shape

Use a required `host_steps` entry when a privileged host-side helper owns the
rules:

```toml
[[target_defaults.host_steps]]
name = "network-policy"
required = true
timeout = "30s"
command = ["/opt/aw-gateway/bin/container-firewall", "add", "{container_pid}"]

[target_defaults.host_steps.health_check]
type = "command"
command = ["/opt/aw-gateway/bin/container-firewall", "check", "{container_pid}"]
```

Host step commands default to a `60s` timeout when `timeout` is omitted. Set a
larger timeout only when the policy helper has a known longer setup path.

If the helper needs elevated privileges, configure that in the host OS, for
example with a narrow `sudoers` rule for only that helper and action. Keep the
gateway config explicit; do not hide privileged behavior behind broad shell
wrappers.

Use a `container_bootstrap_steps` entry when the rules are intentionally
container-owned:

```toml
[[target_defaults.container_bootstrap_steps]]
name = "container-firewall"
required = true
user = "root"
command = ["/opt/site-policy/bin/container-firewall", "add-self"]
```

That model requires the container to have the firewall tool and the runtime
capabilities needed by the command.

## Linux Namespace Example

A host-side helper can enter the container network namespace by PID and manage
iptables there:

```bash
#!/usr/bin/env bash
set -euo pipefail

action="${1:?action required}"
pid="${2:?container pid required}"

[[ "$pid" =~ ^[0-9]+$ ]] || { echo "invalid pid" >&2; exit 2; }
[[ -d "/proc/$pid" ]] || { echo "pid not found" >&2; exit 2; }

ns() {
  nsenter -t "$pid" -n -U "$@"
}

case "$action" in
  add)
    ns iptables -N AW_EGRESS 2>/dev/null || true
    ns iptables -F AW_EGRESS
    ns iptables -D OUTPUT -j AW_EGRESS 2>/dev/null || true
    ns iptables -A OUTPUT -j AW_EGRESS

    ns iptables -A AW_EGRESS -m state --state ESTABLISHED,RELATED -j ACCEPT
    ns iptables -A AW_EGRESS -d 127.0.0.0/8 -j ACCEPT
    ns iptables -A AW_EGRESS -p udp --dport 53 -j ACCEPT
    ns iptables -A AW_EGRESS -p tcp --dport 53 -j ACCEPT
    ns iptables -A AW_EGRESS -j DROP
    ;;
  check)
    ns iptables -C OUTPUT -j AW_EGRESS
    ns iptables -C AW_EGRESS -p udp --dport 53 -j ACCEPT
    ns iptables -C AW_EGRESS -j DROP
    ;;
  status)
    ns iptables -L OUTPUT -n --line-numbers
    ns iptables -L AW_EGRESS -n --line-numbers
    ;;
  *)
    echo "usage: $0 {add|check|status} <container-pid>" >&2
    exit 2
    ;;
esac
```

This example enters both the network namespace and user namespace. That is
useful for rootless Podman-style containers; adapt the `nsenter` flags if your
runtime or kernel policy requires a different privilege model. The policy
allows loopback, established flows, and DNS, then drops the rest. Real
deployments usually add rules for package mirrors, build services, or a proxy
endpoint.

## Transparent Proxy Redirect

A transparent proxy policy usually adds both `nat` and `filter` rules:

- Return loopback traffic without redirection.
- Return traffic generated by the proxy process itself to avoid loops.
- Redirect TCP 80 to the local proxy HTTP/CONNECT port.
- Redirect TCP 443 to the local proxy TLS-intercept port.
- Allow DNS and explicitly approved destinations.
- Drop direct egress that bypasses the proxy.

The repository includes `assets/aw-iptables` as one concrete Linux helper that
uses this shape. Treat it as an example to adapt, not as a universal firewall
policy.

See [Proxy And CA Policy](proxy.md) for the matching proxy service and trust
store pieces.

## Remote Access Flow TLS/TCP

A remote Access Flow route still uses local transparent interception. The
network namespace redirects workload TCP port 80 to the relay's HTTP loopback
listener and TCP port 443 to its HTTPS loopback listener. The embedded relay
then opens a separate TLS/TCP connection to the configured remote Proxy
listener.

The filter policy must permit that outer connection without opening general
web egress:

- allow established and related traffic;
- allow loopback so redirected workload traffic reaches the relay;
- allow only the required DNS resolver when a DNS address is configured;
- allow TCP only to the provisioned Proxy address and exact Access Flow
  listener ports;
- redirect workload TCP 80 and 443 to the corresponding loopback relay ports;
- drop direct TCP 80/443 and every other unapproved egress path; and
- on the Proxy host, accept the Access Flow listener ports only from the
  intended relay network and apply the Proxy's configured source/global abuse
  controls.

For the shipped example shape, those are local relay ports `3128` and `3129`
and remote Proxy ports `7443` and `7444`. Replace all example values. A
production firewall should use stable provisioned Proxy IP addresses. The
route may independently use a DNS `server_name` for certificate verification.
If `address` itself is DNS-named, the firewall owner must maintain the exact
approved resolved address set as part of the same bounded deployment
transaction; DNS changes do not automatically update firewall rules.

Do not use a process-UID bypass as the only exception when workloads can run
under the same UID as `aw-container-agent`. A destination-and-port exception is
the enforceable boundary in that deployment. The repository's existing
`aw-iptables` and `aw-transparent-uds-firewall` assets demonstrate other
topologies and must not be reused unchanged for remote TLS: their local-proxy
exceptions do not establish the remote address/port policy above.

TLS authenticates ACL Proxy to the relay, but it does not authenticate the
relay or workload. The required AWAF bearer remains the sole workload
authentication input. Do not terminate the outer TLS connection at a load
balancer or middlebox; doing so would require a separate trusted second-hop and
bearer-forwarding design. A completely network-disabled container also
requires a separate constrained forwarding mechanism and is not delivered by
this transport.

Make firewall installation or validation a required relay prerequisite before
SSH or workload services become ready. The repository TLS examples intentionally
do not name a site firewall service because the safe rules depend on concrete
addresses, runtime namespaces, and privilege ownership. Add the deployed
service to `access_flow_relay.start_after_services`, and make dependent services
wait on `@access-flow-relay`.

Verify both halves of the policy:

1. Transparent HTTP and HTTPS reach an allowed destination through the remote
   Proxy.
2. A denied destination is rejected by Proxy policy.
3. Direct TCP 80/443 and an unapproved external port fail.
4. Removing the remote Proxy allow rule fails closed.
5. Stopping the Proxy produces no direct, Unix, stale-trust, or alternate
   endpoint fallback.

## Colima Notes

When `aw-gateway` runs on macOS against Colima, the containers live inside the
Colima Linux VM. macOS cannot directly `nsenter` the container namespace. Use
one of these models instead:

- Run policy inside the container through a bootstrap step and grant the
  required runtime capabilities.
- Run VM-level rules with `colima ssh --profile <name> -- sudo iptables ...`.
- Keep the Colima profile dedicated to this policy so bridge-level rules do not
  affect unrelated containers.

VM-level bridge rules commonly target Docker's `docker0` interface inside the
Colima VM. That model is useful for demos and local policy, but it is broader
than a single target container.

## Verification

Add a read-only check action and wire it as a `host_steps.health_check` command.
At minimum, test:

```bash
aw-gateway --config /etc/aw-gateway/gateway.toml up default --json
aw-gateway --config /etc/aw-gateway/gateway.toml run default -- curl -I https://example.com
aw-gateway --config /etc/aw-gateway/gateway.toml run default -- curl -I https://blocked.invalid
```

The exact expected results depend on the policy. Keep the verification commands
next to the policy helper so operators can audit both together.
